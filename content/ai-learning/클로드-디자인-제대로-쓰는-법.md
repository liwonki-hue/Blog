프롬프트 몇 줄로 화면을 만들고, 말로 수정하고, 반응형까지 자동으로 처리해 주는 **클로드 디자인**(Claude Design)의 사용법을 기본기부터 디자인 시스템, 자동 검수까지 단계별로 정리했다. 그리고 영상에서 다루지 않은 부분, 즉 처음 시작할 때 헷갈리기 쉬운 용어와 모델 선택 기준, 결과물을 실제로 써먹는 법까지 보충해서 담았다.

## 클로드 디자인이란

클로드 디자인은 프롬프트 한 번에 디자인 시안 한 장을 뽑아 주는 도구가 아니다. 클로드와 대화하면서 화면을 만들고, 계속 수정하고, 새 페이지로 확장해 나가는 **작업 환경**에 가깝다. 결과물은 클로드에게 다시 수정을 요청할 수도 있고, 에디터 모드에서 사람이 직접 세부 값을 고칠 수도 있다. 나아가 디자인 시스템과 스킬을 연결해서 반복 작업을 줄이고, 결과물을 클로드 코드로 넘겨 실제 작동하는 프로토타입까지 이어갈 수 있다.

클로드 디자인은 이 글을 쓰는 시점 기준으로 베타 상태이며, 데스크톱 앱 안에서 쓸 수 있다. 무료 플랜에서도 체험은 가능하지만, 실제로 여러 화면을 만들고 반복 수정하려면 유료 플랜의 사용량(토큰)을 꽤 소모한다는 점을 미리 알아 두면 좋다.

> **참고.** 클로드 코드를 이미 쓰고 있다면, 데스크톱 앱을 따로 열지 않고도 클로드 코드 안에서 디자인 캔버스를 미리 체험해 볼 수 있는 기능이 있다(아직 초기 미리보기 단계). 데스크톱 앱 설치가 번거롭다면 이 경로도 확인해 볼 만하다.

## 시작하기 — 화면 구성 익히기

데스크톱 앱을 설치하고 로그인한 뒤, 왼쪽 사이드바의 **디자인** 메뉴를 클릭하면 클로드 디자인 화면으로 들어간다. 처음 보면 버튼이 많아 헷갈릴 수 있어서, 주요 요소를 표로 정리했다.

| 요소 | 역할 |
|---|---|
| 프롬프트 입력창 | 만들고 싶은 화면을 글로 설명하는 곳. 파일 첨부, GitHub 코드 불러오기, 피그마 파일 업로드도 여기서 한다. |
| 디자인 시스템 선택 | 특정 스타일(컬러, 폰트, 컴포넌트 규칙)을 고정해 두고, 이후 모든 작업에 같은 스타일을 적용하는 기능. 기본 프리셋 6종을 제공하고, 직접 만든 디자인 시스템도 연결할 수 있다. |
| 코드베이스로 시작 | 이미 가진 코드를 기준으로 디자인을 이어가는 모드. |
| 모델 선택 | 결과물을 생성할 AI 모델을 고른다. 아래 "모델은 뭘 골라야 할까"에서 더 자세히 다룬다. |
| 템플릿 | 모바일 앱, 슬라이드, 문서, 와이어프레임, 애니메이션, 3D 오브젝트, 이메일 HTML까지 다양한 템플릿을 제공한다. 웹 UI 전용 도구가 아니다. |

처음 써 본다면 템플릿 없이 **빈 작업(블랭크)**으로 시작해서 기본 흐름부터 익히는 것을 권한다.

## 기본 사용법 — 만들고, 수정하고, 반응형까지

**1) 프롬프트로 첫 화면 만들기**
"어떤 화면을 만들지, 구성은 어떻게 할지, 전체적인 스타일 톤은 어떤지" 정도만 간단히 적어도 꽤 쓸 만한 결과가 나온다. 예를 들어 "데스크톱 대시보드를 만들어 줘. 사이드바가 있고, 화려하기보다는 깔끔한 SaaS 스타일로"처럼 짧게 요청해도 1~2분 안에 사이드바, 메인 영역을 갖춘 화면 하나가 완성된다.

**2) 코멘트로 부분 수정 요청하기**
화면 특정 구간을 클릭하거나 영역을 드래그해서 코멘트를 남길 수 있다. "이 영역에 아이콘을 넣어 줘", "여기에 그래프를 추가해 줘"처럼 여러 개의 코멘트를 남긴 뒤, 한꺼번에 클로드에게 전달하면 모든 요청을 종합해서 한 번에 반영해 준다. 팀원을 초대해서 함께 코멘트를 남기고, 모은 의견을 한 번에 넘기는 것도 가능하다.

**3) 직접 수정하기 — Edit 모드**
사소한 값(폰트 크기, 두께, 여백, 정렬)까지 매번 말로 요청하면 느리고 비효율적이다. 이럴 때는 화면 오른쪽 위의 **Edit 모드**로 들어가 직접 값을 바꾸면 된다. Edit 모드에는 두 단계가 있다.

- **Simple** — 색상, 폰트, 크기처럼 단순한 속성만 간단히 조정.
- **Pro** — 실제 코드 수준까지 들여다보며 세밀하게 조정. 크기 조정 방식(고정값/내용에 맞춤/영역 꽉 채움) 같은 레이아웃 속성도 여기서 다룬다.

처음에는 Pro 모드의 용어(허그, 필 등 레이아웃 속성)가 낯설 수 있는데, 웹 디자인에서 쓰는 "내용 크기만큼(hug)" vs "영역을 꽉 채움(fill)" 개념과 같다고 생각하면 이해가 쉽다.

**4) 반응형으로 바꾸기**
"반응형으로 처리해 줘"라고 요청하면, 화면 크기별로 레이아웃이 자동으로 바뀐다. 예를 들어 데스크톱에서는 사이드바가 있다가, 중간 크기 화면에서는 상단 메뉴로 바뀌고, 모바일 크기에서는 하단 탭 메뉴로 전환되는 식이다. 결과는 **Present → New Window** 버튼으로 실제 브라우저 창에 띄워서, 창 크기를 줄여 가며 확인할 수 있다.

**5) 스타일을 유지한 채 페이지 확장하기**
"기존 화면의 스타일 방향을 유지하면서 상세 페이지를 추가해 줘"처럼 요청하면, 이미 만든 화면의 색상·톤·구조를 그대로 가져가면서 새 페이지를 만들어 준다. 전에 요청했던 수정 사항까지 기억해서 새 페이지에도 반영해 주는 점이 특히 유용하다.

## 퀄리티를 높이는 법 — 디자인 브리프와 레퍼런스

아무 준비 없이 짧은 프롬프트만 던지면, 사용자가 누구인지·무엇이 가장 중요한지·어떤 UI 패턴을 쓸지 같은 판단을 전부 AI에게 맡기는 셈이다. 결과가 나쁘진 않아도, 내가 원하는 방향과는 다르게 흘러가기 쉽다.

**디자인 브리프 작성하기.** 핵심은 "AI가 대신 판단하면 안 되는 부분"을 내가 미리 정해 주는 것이다. 타깃 사용자가 누구인지, 어떤 기능이 가장 중요한지, 어떤 톤으로 보여 줄지를 구체적으로 적은 문서를 프롬프트로 붙여 넣으면, 막연한 "대시보드 UI"가 아니라 실제 제품처럼 우선순위가 반영된 화면이 나온다. 디자인 브리프의 역할은 화면을 예쁘게 만드는 게 아니라, **AI가 마음대로 결정할 수 있는 영역을 줄이는 것**이다.

**레퍼런스 이미지 활용하기.** 디자인 톤은 주관적인 영역이라, 핀터레스트나 드리블(Dribbble) 같은 사이트에서 평소 마음에 들던 스타일을 2~3장 모아서 함께 넣어 주면 도움이 된다. 이때 중요한 건 요청 방식이다. "기능과 정보 구조, 레이아웃은 그대로 유지하고, 색상·타이포그래피·여백·둥글기·버튼 스타일 같은 **비주얼 톤앤매너만** 레퍼런스를 참고해 줘"처럼 범위를 명확히 제한해야, 구조까지 통째로 바뀌는 걸 막을 수 있다.

디자인 브리프와 레퍼런스를 함께 쓰면, 흔히 보이는 전형적인 "AI가 만든 듯한" 느낌(보라색 그라데이션, 비슷한 카드 배치 같은 패턴)이 눈에 띄게 줄어든다.

## 스타일 재사용하기 — 디자인 시스템 만들기

앱 화면, 슬라이드, 모바일 디자인을 각각 따로 만들면서 매번 같은 컬러·폰트·둥글기 값을 설명하는 건 번거롭고, 설명한다고 매번 똑같이 나온다는 보장도 없다. 이럴 때 쓰는 기능이 **디자인 시스템**이다.

**만드는 순서**

1. 마음에 드는 결과물이 나온 프로젝트를 열고, 새 채팅에서 "이 프로젝트를 디자인 시스템에 최적화된 구조로 정리해 줘"라고 요청한다. 컬러·타이포그래피·여백 같은 기초 요소부터 버튼·입력창 같은 컴포넌트까지 체계적으로 정리해 준다.
2. 정리가 끝나면 **Share → Copy Link**로 링크를 복사한다.
3. 홈 화면에서 **디자인 시스템 → Create Design System → Create Here**를 선택하고, 방금 복사한 링크를 붙여 넣는다. GitHub 코드나 피그마 파일, 로고·폰트 같은 브랜드 에셋이 있다면 이 단계에서 함께 넣을 수 있다.
4. 생성이 끝나면 컬러, 컴포넌트, 모션, 타입 스케일 같은 항목이 제대로 정리됐는지 검수한다.

**활용하기**
새 프로젝트를 시작할 때 방금 만든 디자인 시스템을 선택하고 "슬라이드를 만들어 줘", "모바일 앱 화면 3개를 만들어 줘"처럼 요청하면, 형식이 완전히 달라도 색상·컴포넌트·둥글기 같은 비주얼 언어가 일관되게 적용된다. 한 번 만든 디자인을 그때그때 버리는 게 아니라, **재사용 가능한 자산**으로 쌓아 가는 것이 디자인 시스템의 핵심 효과다.

## 반복 작업 줄이기 — 스킬로 자동 검수하기

여러 화면, 특히 수십~수백 페이지를 만들다 보면 글자·간격·우선순위가 미묘하게 어긋나는 경우가 쌓인다. 사람이 일일이 검수하면 시간이 오래 걸리고 놓치는 부분도 생긴다. 이럴 때 **스킬**(Skill)을 활용한다.

스킬은 "작업하기 전에 AI가 참고해야 할 기준과 절차"를 재사용 가능한 문서로 만들어 둔 것이다. 거창할 필요 없이, `이름(name)`과 `설명(description)`을 담은 마크다운 파일(`skill.md`) 하나면 충분하다.

**UX/UI 검수 스킬 만드는 법**

1. `skill.md` 파일에 검수 원칙(시각적 우선순위, 레이아웃과 간격, 타이포그래피, 색상 같은 항목별 기준과 심각도 분류)을 적는다. AI가 이미 알 만한 당연한 내용까지 적을 필요는 없고, 내 기준에서 중요한 것만 적으면 된다.
2. 클로드 앱 좌측 하단의 계정 메뉴 → **설정 → 스킬(사용자 지정)**로 들어가서, 우측 상단 **추가하기 → 스킬 업로드**로 `skill.md` 파일을 드래그해 올린다.
3. 업로드 후에는 클로드 디자인을 껐다 켜야 새 스킬이 반영된다.
4. 디자인 화면에서 좌측 하단 **+ → Skills**를 눌러 방금 등록한 스킬을 선택(Use)하고, "UX/UI적으로 문제가 있는지 검수해 줘"라고 요청한다.

결과로는 문제 영역과 심각도, 개선 제안이 정리되어 돌아온다. 제안을 전부 그대로 받아들일 필요는 없고, 마음에 드는 부분만 골라 "이 부분만 반영해 줘"라고 다시 요청하면 된다. 검수 외에도 기획 단계의 원칙이나 UX 라이팅 톤 같은 것도 스킬로 만들어 두면, 이후 모든 작업이 그 범위를 크게 벗어나지 않는다. 내용이 많아지면 하나의 파일에 다 넣지 말고, 접근성·SEO·반응형처럼 주제별로 파일을 나눠 관리하는 쪽이 정리하기 편하다.

## 영상에는 없는, 처음 쓸 때 도움 되는 팁

**모델은 뭘 골라야 할까.** 클로드 디자인에서도 작업 성격에 따라 모델을 다르게 고르는 게 비용 대비 효율적이다. 가볍게 연습하거나 구조만 빠르게 확인할 때는 저렴한 모델로 충분하고, 실제로 쓸 결과물이나 디자인 시스템처럼 한 번 잘 만들어 두면 계속 재사용할 작업에는 더 성능 좋은 모델을 쓰는 것이 낫다. 사용량(토큰)은 화면 하나를 만들 때마다 꽤 소모되므로, 비슷한 요청을 반복하기보다 프롬프트 한 번에 원하는 내용을 최대한 구체적으로 담는 습관이 비용을 아끼는 데 도움이 된다.

**Interact 모드와 Comment 모드를 구분해서 쓰자.** 기본값인 Interact 모드에서는 화면 요소를 클릭해 반응을 확인할 수 있고, Comment 모드에서는 특정 영역에 의견만 남길 수 있다. 수정 의도를 정확히 전달하려면 애매한 영역 전체에 말로 설명하기보다, Comment 모드로 정확한 위치를 짚어 주는 쪽이 훨씬 효율적이다.

**결과물을 실제로 작동하게 만들려면.** 클로드 디자인에서 나온 화면은 기본적으로 정적인 UI다. 버튼을 눌러도 실제 기능은 동작하지 않는다. 실제로 작동하는 서비스로 만들려면, 완성된 디자인을 클로드 코드로 넘겨서 구현을 요청하면 된다. 이후 GitHub에 코드를 올리고 Vercel로 배포하는 과정은, 이전 글 [나만의 웹사이트 만들기]({{< ref "나만의-웹사이트-만들기" >}})에서 다룬 흐름과 동일하다.

**처음에는 완벽을 기대하지 말 것.** 디자인 브리프도, 디자인 시스템도, 검수 스킬도 한 번에 완성되지 않는다. 일단 간단한 버전으로 만들어 써 보고, 아쉬운 점이 생길 때마다 조금씩 보강해 나가는 쪽이 실제로 끝까지 쓰게 되는 방법이다.

## 마무리

클로드 디자인은 프롬프트만으로 화면을 뽑아내는 재주 부리기용 도구가 아니라, **브리프로 방향을 잡고, 디자인 시스템으로 스타일을 고정하고, 스킬로 반복 작업을 줄이는** 하나의 작업 환경에 가깝다. 처음엔 짧은 프롬프트로 가볍게 시작하고, 결과물이 쌓이면 디자인 시스템으로 묶고, 반복되는 검수나 규칙은 스킬로 저장해 나가는 순서로 익히면 어렵지 않게 손에 붙는다.
